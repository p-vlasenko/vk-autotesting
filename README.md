## ДЗ-1: автотесты REST API Restful Booker

Автотесты для публичного API бронирований **Restful Booker**: https://restful-booker.herokuapp.com
Документация: https://restful-booker.herokuapp.com/apidoc/index.html

тест-кейсы и дефекты API — в [docs/TEST_CASES.md](docs/TEST_CASES.md).

### Стек
Kotlin (JVM 21), Gradle 9 (Kotlin DSL, wrapper), JUnit 5, REST Assured (+ kotlin-extensions, json-schema-validator), Jackson (jackson-module-kotlin), Datafaker, AssertJ.

### Тестируемые эндпоинты
| Метод | Путь | Тесты |
|---|---|---|
| GET | `/ping` | HC-1 |
| POST | `/auth` | AU-1, AU-2 |
| POST | `/booking` | CR-1 … CR-7 |
| GET | `/booking`, `/booking/{id}` | GT-1 … GT-8 |
| PUT, PATCH | `/booking/{id}` | UP-1 … UP-3 |
| DELETE | `/booking/{id}` | DL-1 … DL-4 |

### Сценарии
- **Позитивные:** проверка доступности (ping); получение токена; создание брони, в том числе без необязательного поля; чтение по ID с проверкой JSON Schema; список, фильтры по имени и по датам `checkin`/`checkout`; PUT, PATCH и DELETE с токеном в cookie и с Basic auth.
- **Негативные:**
  - неверные креды (3 варианта);
  - бронь без обязательного поля (5 вариантов) — бронь не создаётся;
  - невалидный JSON и пустой объект;
  - удалённый и нечисловой ID дают 404;
  - `Accept: text/plain` даёт 418;
  - PUT, PATCH и DELETE без авторизации и с невалидным токеном дают 403, данные не меняются.
- **Граничные:** `totalprice = 0`; однодневная бронь (`checkin == checkout`); строки по 300 символов, кириллица, спецсимволы и emoji.

Каждая изменяющая операция дополнительно проверяется повторным GET. В PUT каждое поле гарантированно отличается от исходного. Если создание отклонено (или должно быть отклонено — `@KnownBug`), тест ищет бронь по уникальным именам и проверяет, что она не сохранилась. Ответ GET сравнивается с отправленными данными, а не с ответом POST. Структура ответа `GET /booking/{id}` и списка `GET /booking` проверяется JSON Schema. Десериализация в DTO не приводит типы: `"777"` вместо числа или `"true"` вместо boolean роняют тест. Для текстовых ответов API (ошибки, `201 Created`) проверяются точные статус, `Content-Type: text/plain` и тело (`Forbidden`, `Not Found`, …): так тест на валидацию не позеленеет от случайного `503` упавшего стенда.

### Как устроено
```
src/test/kotlin/booker/
  config/   ApiConfig (параметры), Specs (Request/ResponseSpecification)
  logging/  лог HTTP при падении теста с маскировкой секретов
  models/   DTO: Booking, BookingDates, CreateBookingResponse, AuthRequest/Response, Auth
  clients/  AuthClient, BookingClient, HealthClient — только HTTP, без проверок
  data/     BookingBuilder — валидная бронь на Datafaker (seed) + UUID
  support/  JUnit-инфраструктура: BookingTracker (учёт и удаление броней), StandAvailability
            (проверка стенда перед прогоном), @KnownBug, AbortOnTransportError, AuthKind
  tests/    BaseTest (клиенты, авторизация, данные, хелперы) и тестовые классы
  infra/    локальные тесты инфраструктуры (без стенда): маскировка, BookingTracker на поддельном
            HTTP-сервере, AbortOnTransportError, строгий маппер, воспроизводимость данных
src/test/resources/schemas/  booking.json, booking-list.json
```
- **Изоляция данных.** Каждый тест сам создаёт брони с уникальными именами, а `BookingTracker` удаляет их после теста. ID регистрируется сразу после ответа, до проверок, поэтому бронь удаляется, даже если проверка ответа упала. Брони, найденные поиском в негативных сценариях создания, тоже регистрируются. Удалённой бронь считается, только если DELETE вернул `201` или следующий GET вернул `404`: `405` сам по себе не доказывает, что брони нет. Если тест уже подтвердил удаление сам, бронь снимается с учёта. Если удаление не удалось, тест падает, а у уже упавшего теста ошибка очистки добавляется к причине падения как suppressed. Чужие брони не читаются и не меняются, ID не перебираются. Тесты запускаются последовательно.
- **Воспроизводимые данные.** Данные теста целиком определяются тремя параметрами: `booker.seed` (значения Datafaker и суффиксы имён), `booker.runId` (часть каждого имени, разводит запуски на общем стенде) и `booker.baseDate` (от неё считаются даты). Если параметры не заданы, seed и `runId` случайные, а дата — сегодняшняя. Каждый тест получает свой генератор от seed и имени теста, поэтому его данные повторяются и при отдельном запуске. При падении печатается готовая строка `-Dbooker.seed=… -Dbooker.runId=… -Dbooker.baseDate=…`. Повтор с тем же seed и новым `runId` даёт те же значения с новыми именами: так не будет пересечения с бронями прошлого запуска, если их не удалось удалить.
- **Проверка стенда.** Перед первым тестовым классом `GET /ping` опрашивается каждые 3 с, пока стенд не ответит `201` или не истечёт `booker.standWait` (по умолчанию 60 с): Heroku после простоя «просыпается» дольше одного таймаута. Если стенд так и не ответил, один класс падает с причиной (`Stand … is unavailable after … ms: …`), остальные тесты прерываются (aborted), без ожидания таймаута в каждом тесте. Проверка выполняется один раз за прогон: если стенд пропадёт посреди прогона, следующие тесты упадут по таймауту.
- **Без фиксированных пауз в тестах** и без проверок времени ответа. Единственный `Thread.sleep` — интервал между попытками `GET /ping` в `StandAvailability`: это опрос с ограничением `booker.standWait`, а не ожидание «на всякий случай».
- **Лог при падении.** Если тест упал, в консоль и в HTML-отчёт выводятся seed и все его запросы и ответы, в том числе запрос, на который ответа не было: таймаут или ошибка соединения. Заголовки `Authorization`, `Cookie`, `Set-Cookie` заменяются на `***`. Тело разбирается как JSON, и поля `token`/`password` маскируются на любой глубине. Тело, которое не разбирается как JSON, но упоминает эти поля, не выводится.

### Окружение и запуск
Нужны JDK 21 и доступ в интернет. Gradle скачивается через wrapper.

```bash
./gradlew test                                      # основной набор
./gradlew test --tests "booker.tests.AuthTest"      # один класс
./gradlew test -Dbooker.baseUrl=http://localhost:3001   # другой стенд
./gradlew test -Dbooker.seed=42 -Dbooker.runId=abc -Dbooker.baseDate=2026-10-11   # повторить данные
./gradlew test --tests "booker.infra.*"             # только локальные тесты инфраструктуры
xdg-open build/reports/tests/test/index.html        # HTML-отчёт

./gradlew knownBugs                                 # тесты известных дефектов
xdg-open build/reports/tests/knownBugs/index.html
```

Задача `test` не кэшируется (`outputs.upToDateWhen { false }`): тесты ходят во внешний API, поэтому повторный `./gradlew test` всегда выполняет их заново.

Все параметры — в `ApiConfig`, задаются через `-D` или переменные окружения. Если не заданы, берутся значения по умолчанию:

| Property | Env | По умолчанию |
|---|---|---|
| `booker.baseUrl` | `BOOKER_BASE_URL` | `https://restful-booker.herokuapp.com` |
| `booker.connectTimeout` | `BOOKER_CONNECT_TIMEOUT` | `30000` мс |
| `booker.readTimeout` | `BOOKER_READ_TIMEOUT` | `15000` мс |
| `booker.standWait` | `BOOKER_STAND_WAIT` | `60000` мс — сколько ждать ответа `/ping` перед прогоном |
| `booker.username` | `BOOKER_USERNAME` | `admin` |
| `booker.password` | `BOOKER_PASSWORD` | `password123` |
| `booker.seed` | `BOOKER_SEED` | случайный, печатается при падении |
| `booker.runId` | `BOOKER_RUN_ID` | случайные 8 символов, печатается при падении |
| `booker.baseDate` | `BOOKER_BASE_DATE` | сегодня, печатается при падении |

`admin` / `password123` — публичные демо-креды из документации API. Других секретов в репозитории нет.

### Как тестируются известные дефекты
У каждого дефекта есть два теста:
- **в основном наборе** (`./gradlew test`) — фиксирует текущее ошибочное поведение точно: код, `Content-Type`, тело. Имя теста помечено `[known bug: текущее поведение]`. Если API исправят, тест упадёт и подскажет, что ожидание пора менять;
- **с `@KnownBug`** (тег `known-bug`) — проверяет правильное поведение. Из основного прогона исключён, запускается `./gradlew knownBugs`. Задача не роняет сборку (`ignoreFailures`). **Полезный сигнал здесь один: PASSED означает, что дефект исправлен.** Для дефектов создания PASSED требует и правильного ответа, и того, что бронь не сохранилась: ответ `400` с сохранённой бронью тест не пропустит. FAILED сам по себе не доказывает дефект. Воспроизведение доказывают зелёные тесты основного набора с пометкой `[known bug]`, потому что они проверяют точный ответ. Чтобы сбой стенда не выглядел как «дефект на месте», транспортные ошибки (DNS, таймаут, обрыв соединения, TLS) в `@KnownBug`-тестах превращаются в aborted (skipped). Ошибки разбора ответа (Jackson) к ним не относятся: стенд ответил, тест падает. Ошибка очистки после теста тоже остаётся падением.

### Найденные дефекты
| Дефект | Факт | Ожидание | Тесты |
|---|---|---|---|
| Нет поля из обязательных (`firstname`, `lastname`, `totalprice`, `depositpaid`, `bookingdates`) | 500 `Internal Server Error` | 400 | CR-5 |
| Пустой объект `{}` | 500 `Internal Server Error` | 400 | CR-6b |
| Отрицательная `totalprice` | 200, бронь создана | 400 | CR-7a |
| `checkout` раньше `checkin` | 200, бронь создана | 400 | CR-7b |
| DELETE уже удалённой брони с токеном | 405 `Method Not Allowed` | 404 | DL-4 |
| Фильтр `checkin=D` не находит бронь с заездом ровно в `D` | заезд > `D` | заезд ≥ `D` (по документации) | GT-8 |
| Фильтр `checkout=D` расходится с документацией | выезд ≤ `D` | выезд ≥ `D` (по документации) | GT-8 |

Фильтры по датам расходятся с документацией. Здесь может ошибаться как реализация, так и документация. Для `checkout` поведение «до даты» выглядит осмысленным, и, возможно, неточна именно документация. В тестах это помечено как known bug, потому что контрактом считается документация. Случаи со сдвигом 0 дней зависят от того, как сервер приводит даты, включая часовой пояс. Если GT-8 начнёт флакать после передеплоя стенда, первым делом стоит проверить именно их.

### Особенности API (тестируются как есть)
- Неверные креды в `/auth` возвращают **200** и `{"reason":"Bad credentials"}`, а не 401.
- Изменение без авторизации или с невалидным токеном возвращает **403**, а не 401.
- `Accept: text/plain` даёт **418 I'm a Teapot**. Список из нескольких JSON-типов тоже даёт 418: например, `application/json, text/json`, который REST Assured по умолчанию отправляет для `ContentType.JSON`. Поэтому в спецификации `Accept` задан строкой `application/json`.
- Синтаксически невалидный JSON корректно возвращает **400** (CR-6a).
- Ошибки и `201 Created` приходят как `text/plain` с телом-названием статуса (`Forbidden`, `Not Found`, `I'm a Teapot`, …), а не JSON.

### Ограничения и что не тестировалось
- **401** — API этот код не использует.
- **BOLA/IDOR** — в API нет пользователей и владельцев ресурсов, только один демо-аккаунт.
- **409** и **Problem Details** — не предусмотрены контрактом.
- **Время ответа, нагрузка, перебор ID** — не проверяются: это чужой публичный стенд.
- Ограничение длины строк не документировано. Тест CR-4 фиксирует фактическое поведение: 300 символов принимаются.
- Стенд общий: его могут периодически сбрасывать, а после простоя он долго «просыпается» на Heroku. Поэтому connect timeout увеличен, а каждый тест создаёт свои данные. Сбой сети или стенда виден в логе упавшего теста как `<-- NO RESPONSE: …` (например, `UnknownHostException` или `SocketTimeoutException`): такое падение говорит о недоступности стенда, а не о дефекте API. Если из-за сбоя не удалось удалить созданную бронь, тест падает с `Cleanup failed` и ID этой брони.
- Если ответ на `POST /booking` не пришёл (таймаут чтения), бронь на сервере могла создаться, но её ID неизвестен. Удалить такую бронь тест не может, и сообщить о ней тоже: это ограничение API без идемпотентного создания. Найти её можно по уникальному имени из лога упавшего теста.
